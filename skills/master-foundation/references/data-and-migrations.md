# البيانات، الحذف، الترحيلات، الخصوصية

## 1. العمليات التدميرية

**تحتاج موافقة كتابية صريحة من المطور + عرض الأثر قبل التنفيذ:**

| الفئة | أمثلة |
|:---|:---|
| قاعدة البيانات | `DROP`, `TRUNCATE`, `DELETE` بلا `WHERE` أو على نطاق واسع، حذف أعمدة/جداول، `prisma migrate reset`, `supabase db reset`, `db push --force` |
| الملفات | `rm -rf` خارج مجلدات مؤقتة/ناتج البناء، `find ... -delete` |
| Git | `git reset --hard`, `git clean -fd`, `git push --force`, حذف فروع بعيدة، إعادة كتابة التاريخ |
| الحاويات والسحابة | `docker volume prune`, `docker system prune`, حذف bucket/مورد سحابي |

**مسموح دون سؤال** (غير تدميري في بيانات المطور): حذف ملفات مؤقتة أنشأتها أنت في هذه الجلسة، ومجلدات الناتج القابلة لإعادة التوليد (`dist`, `.next`, `node_modules`).

### حسب البيئة

| البيئة | القاعدة |
|:---|:---|
| محلية مؤقتة (بيانات اختبار) | إعادة الضبط بعد تأكيد المطور |
| مشتركة (staging/preview) | ممنوع دون موافقة صريحة |
| إنتاج | **الوكيل لا يملك بيانات اعتمادها أصلاً** |

إن اكتشفت أنك متصل ببيئة غير محلية، توقف وأخبر المطور.

## 2. الحذف المنطقي هو الافتراضي

حين يطلب المستخدم "حذف" داخل التطبيق: `deleted_at = now()` أو `status = 'archived'`.

- كل الاستعلامات تستثني المحذوف افتراضياً (Scope/View).
- تذكّر: الحذف المنطقي **يُبقي البيانات** ولا يحقق طلب المسح النظامي.

## 3. مسح البيانات الشخصية (الحق في المحو)

> هذا إرشاد تقني، وليس استشارة قانونية. راجع مختصاً بخصوص PDPL/GDPR ومدد الاحتفاظ الإلزامية.

- **التجهيل (Anonymization)**: تفريغ الحقول المعرِّفة (اسم، بريد، هاتف، عناوين، معرّفات خارجية) بقيم لا يمكن عكسها، مع الإبقاء على الصف للحفاظ على سلامة المفاتيح الأجنبية والإحصاءات. سجّل `anonymized_at`.
- **التشفير ليس تجهيلاً**: البيانات المشفرة قابلة للاستعادة بالمفتاح، فهي pseudonymization فقط.
- **الحذف الفعلي** مقبول (وأحياناً مطلوب) حين تقرره سياسة احتفاظ يعتمدها المطور، ويُنفَّذ عبر مهمة مجدولة مراجَعة، وليس بقرار من الوكيل منفرداً.
- لا تنسَ النسخ الاحتياطية والسجلات والتحليلات ومزوّدي الطرف الثالث.
- دعم تصدير بيانات المستخدم، وجمع الموافقة الصريحة، وتحديد فترات الاحتفاظ.

## 4. الترحيلات (Migrations)

قبل أي ترحيل:
1. اعرض SQL الناتج للمطور وراجعه (لا تشغّل ترحيلاً لم تقرأ نصه).
2. تأكد من وجود نسخة احتياطية أو نقطة استرجاع.
3. جرّبه على بيئة محلية/فرع قاعدة بيانات أولاً.
4. فضّل نمط **expand → migrate → contract**: أضف الجديد، انقل البيانات، وبعد التأكد (في ترحيل لاحق وبموافقة) احذف القديم.
5. تغييرات الأعمدة التدميرية (حذف/تغيير نوع) تحتاج موافقة صريحة.
6. الجدول الجديد الذي يحوي بيانات خاصة: `deleted_at` + RLS/نطاق + اختبار العزل في نفس الترحيل.
7. أضف خطة تراجع (Rollback) مكتوبة.

## 5. سجل التدقيق

جدول إضافة فقط (`INSERT`)، بلا `UPDATE/DELETE` عبر الصلاحيات، وبلا أسرار أو PII خام.
