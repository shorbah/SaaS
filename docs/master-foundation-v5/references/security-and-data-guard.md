# أمان البيانات وحدود الوصول (Security & Data Guard)

> مرجع هندسي عالمي لإدارة أمان البيانات، حدود الصلاحيات، وحماية المعلومات الحساسة لأي نظام برمجي.

---

## 1. سياسة الحظر المطلق لتدمير البيانات (Zero Data Destruction Policy)

> 🛑 **قاعدة أمان غير قابلة للتفاوض:**  
> **يُحظر تماماً على الوكيل البرمجي كتابة أو تنفيذ أي عمليات حذف فعلي نهائي للبيانات (`DROP TABLE`, `TRUNCATE`, `HARD DELETE`, مسح قواعد البيانات أو الملفات) تحت أي ظرف.**

### الضوابط التشغيلية:
1. **الحذف الافتراضي دائمًا منطقي (Logical / Soft-Delete):**  
   أي عملية حذف يطلبها المستخدم في النظام تُترجم برمجياً إلى تعيين طابع زمني أو حالة أرشفة:
   - `archived_at = now()` أو `deleted_at = now()` أو `status = 'archived'`.
2. **استثناء وحيد:**  
   لا يتم تنفيذ أي حذف نهائي من الجداول أو قواعد البيانات إلا إذا أصدر المطور البشري **أمراً كتابياً صريحاً ومباشراً** يطلب فيه الحذف النهائي بالاسم، مع استعراض تأثير الحذف مسبقاً قبل التنفيذ.

---

## 2. عزل حدود الوصول وتعدد المستخدمين (Boundary Isolation)

عندما يتعامل التطبيق مع حسابات متعددة، أو منظمات مختلفة، أو صلاحيات متباينة:

### القاعدة المعمارية:
> **حدود الأمان تُفرض دائماً في طبقة التخزين (Database / Storage Layer) أو طبقة خدمات الخادم (Server Domain Services)، ويُحظر الاعتماد على تصفية الواجهة الأمامية.**

### أنماط التنفيذ الموصى بها:
1. **عزل الصفوف في قاعدة البيانات (Row-Level Isolation):**
   - في قواعد البيانات التي تدعم سياسات الأمان (مثل PostgreSQL RLS): تفعيل سياسات الأمان على كافة الجداول التي تحتوي بيانات خاصة بمستخدم أو جهة معينة.
   - ربط الاستعلامات دائماً بمعرّف النطاق الموثق في جلسة المصادقة (`auth context` / `session`).
2. **النطاق الشامل في الاستعلامات (Scoped Queries / ORM Global Scopes):**
   - في قواعد البيانات الأخرى: استخدام Middleware أو Global Query Scopes يضمن إلحاق معرّف النطاق تلقائياً في كل استعلام قراءة أو كتابة.

## 3. حماية الحقول الحساسة (Restricted Fields Protection)

> **مبدأ:** "البيانات التي لا يملك المستخدم صلاحية رؤيتها، لا يجب أن تخرج من الخادم أصلاً."

### ❌ الممارسة الخاطئة:
إرسال الكائن بالكامل من قاعدة البيانات إلى الواجهة الأمامية، ثم إخفاء الحقول الحساسة (مثل الأسرار، الأرقام المالية، البيانات الشخصية) عبر إخفائها في مكون الواجهة (CSS أو `display: none`).

### ✅ الممارسات المعمارية الصحيحة:
1. **فصل الكيانات الحساسة في جداول/نماذج مستقلة:**
   - عزل الحقول العامة في نموذج أساسي (`entities`).
   - وضع الحقول الحساسة في نموذج فرعي بنسبة 1:1 (`entity_secrets` أو `entity_financials`) محمي بسياسات وصول مشددة تمنع القراءة إلا للرتب المصرحة.
2. **عزل النوافذ في قاعدة البيانات (Security Views):**
   - إنشاء Views تعيد الحقول العامة فقط، وتستبدل الحقول المقيدة بقيم فارغة (`NULL`) لغير المصرح لهم.
3. **طبقة إسقاط البيانات (Server DTO Projection):**
   - في واجهات البرمجة (REST / GraphQL / tRPC): تطبيق Data Transfer Objects (DTO) تسقط فقط الحقول المسموح بها للمستخدم الحالي قبل إرسال الاستجابة.

---

## 4. الخصوصية وسجلات التدقيق (Privacy & Audit Logging)

1. **سجل التدقيق غير القابل للتلاعب (Append-only Audit Log):**
   - تسجيل كافة العمليات الحساسة (تسجيل الدخول، تعديل الصلاحيات، الوصول للبيانات المحمية) في جدول تدقيق يُسمح فيه بالإضافة فقط (`INSERT`) ويُمنع فيه التعديل أو الحذف (`UPDATE / DELETE`).
2. **الامتثال العام للوائح الخصوصية (GDPR / PDPL / CCPA):**
   - طلب الموافقة الصريحة عند جمع بيانات تعريفية.
   - دعم تصدير بيانات المستخدم عند الطلب.
   - احترام فترات الاحتفاظ النظامية بالبيانات قبل أرشفة أو تنظيف السجلات.

---

## 5. نظافة الأسرار ومفاتيح المصادقة (Key Hygiene)

- لا يتم تضمين أي مفاتيح خاصة، أو كلمات سر، أو رموز توثيق داخل مستودع الكود (Git).
- الفصل الصارم بين المفاتيح العامة (التي تُمرر لمتصفح العميل أو تطبيق الجوال) والمفاتيح السرية الحصرية ببيئة الخادم الموثوقة.
- التحقق الصارم من صحة المدخلات (Validation Schemas) في نقطة الدخول قبل التعامل مع أي مدخل قادم من خارج النظام.
