# سجل القرارات الهندسية (Requests Ledger)

---

## الغرض الأساسي

تسجيل القرارات المعمارية المفصلية، التصحيحات التوجيهية من المطور، والدروس المستفادة، لبناء ذاكرة تراكمية للمشروع.
**هذا السجل ليس لتدوين نصوص الطلبات الحرفية أو التعديلات الروتينية، بل للقرارات التي تؤثر على توجه الوكيل البرمجي مستقبلاً.**

---

## مسار السجل

```
docs/audit/requests_ledger.jsonl
```

## متى يتم التدوين في السجل؟

يتم تسجيل قيد جديد **فقط** عند تحقق أحد الشروط التالية:
1. **تصحيح معماري (`architectural_correction`):** قيام المطور بتصحيح توجه الوكيل واختيار معمارية بديلة.
2. **قرار تصميمي حاسم (`design_decision`):** حسم المفاضلة بين تقنيتين أو نمطين برمجيين.
3. **درس مستفاد (`lesson_learned`):** اكتشاف ثغرة أو سلوك غير متوقع وتوثيق طريقة تفاديه.

> 🚫 **ما يُمنع تدوينه:** طلبات تعديل النصوص، إصلاح الأخطاء الإملائية، أوامر التشغيل الاعتيادية، المطالبات الحرفية (`raw_prompt`)، أو أي بيانات سرية وحساسة.

## البنية القياسية للسجل (JSONL Schema)

كل سجل هو كائن JSON كامل **في سطر واحد فقط** بدون فواصل أسطر داخلية:

```json
{"ts":"2026-10-27T10:00:00Z","type":"architectural_correction","summary":"ملخص القرار في سطر واحد","decision":"تفاصيل القرار وسببه","tags":["security","architecture"],"feature":"feature-name"}
```

### توصيف الحقول:
| الحقل | الحالة | التوصيف |
|:---|:---|:---|
| `ts` | إلزامي | الطابع الزمني بصيغة ISO 8601 (مثل: `2026-10-27T14:30:00Z`) |
| `type` | إلزامي | أحد الأنواع الثلاثة: `architectural_correction` أو `design_decision` أو `lesson_learned` |
| `summary` | إلزامي | ملخص موجز ومباشر للقرار |
| `decision` | إلزامي | ما تم اعتماده وسبب تفضيله |
| `tags` | اختياري | وسوم لتسهيل البحث والتصنيف |
| `feature` | اختياري | اسم الميزة أو المكون البرمجي المرتبط |

## بروتوكول التعلم الذاتي (Learn from Ledger)

### الضوابط الصارمة:
1. **التعلم بطلب بشري صريح فقط:** لا يقوم الوكيل بالتعلم الذاتي أو استنتاج قواعد جديدة تلقائياً أبداً. يجب أن يطلب المطور صراحة: `"استخرج قواعد من السجل"` أو `"تعلّم من السجل"`.
2. **العرض والموافقة المسبقة:** يقرأ الوكيل آخر 50 سجلاً، ويصيغ مقترحات قواعد محددة، ويعرضها على المطور أولاً للمراجعة والاعتماد.
3. **سقف القواعد (Rule Cap):** لا تتجاوز القواعد المضافة في ملف القواعد حاجز **30 قاعدة** كحد أقصى لمنع تشتت النماذج؛ وإذا زادت، تُدمج القواعد المتشابهة بعد موافقة المطور.
4. **اعتماد بشري إلزامي:** لا يُكتب أي سطر في ملفات القواعد العامة (`AGENTS.md`) إلا بعد موافقة المطور الصريحة.

## التعامل مع Git (.gitignore)

ملف السجل مخصص للمشروع. إذا كانت القرارات المسجلة تتضمن معلومات تجارية خاصة بالفريق يُفضل إبقاؤها محلية، يمكن إضافته لملف `.gitignore`:

```gitignore
# اختياري: إذا رغب الفريق في إبقاء سجل القرارات محلياً
docs/audit/requests_ledger.jsonl
```
