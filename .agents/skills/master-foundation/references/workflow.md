# المسار الهندسي (Workflow)

يُطبَّق على مهام البرمجيات L2 وL3، مع تكييف عمق الإجراءات حسب المخاطر. L1 يأخذ ما يلزم فقط وL0 يتجاوز المسار الكامل. مهام المستندات والعروض والملفات غير البرمجية تتبع `deliverables.md` والمهارة المتخصصة مباشرة.

## 0. الجاهزية (Pre-flight)

- تحقق من **وجود** ملف الإعدادات والمتغيرات المطلوبة دون قراءة قيمها (انظر `security.md`).
- تأكد من أنك على فرع عمل وليس على `main` (انظر `git-and-environments.md`).
- تأكد أن الأدوات/خوادم MCP اللازمة متاحة (مثل `plannotator` و `speckit`). إن لم تكن متاحة أو كانت البيئة بلا متصفح (Headless/SSH)، اعتمد البدائل المحددة في `skills-map.md`.

## 1. الفهم والاستكشاف

1. ابحث أولاً (grep، قائمة المجلدات، رسم العلاقات) لتحديد نطاق التأثير: موضعي أم مشترك (قاعدة بيانات/مكوّنات مشتركة).
2. اقرأ الملفات المستهدفة وما يرتبط بها مباشرة. **قاعدة القراءة التدريجية:** ابدأ بالمقاطع ذات الصلة، واستخدم البحث عن الرموز والاستدعاءات لتحديد نطاق التغيير. للملفات الطويلة، ابدأ عادةً بمقطع تقريبي لا يتجاوز 150–200 سطر ثم وسّع النطاق عند الحاجة. هذا إرشاد وليس سقفاً: اقرأ الملف كاملاً عندما يكون صغيراً أو عندما يتطلب التغيير فهماً شاملاً. لا تكرر قراءة محتوى لم يتغير ولا تحتاج إليه.
3. اتبع الأنماط والمصطلحات الموجودة (types، glossary). لا تخترع نمطاً موازياً.

## 2. التخطيط والأسئلة ومسار المواصفات (SDD)

- **قاعدة الأسئلة والاستيضاح:** لا تسأل إلا عن قرار جوهري لا يمكن استنتاجه بثقة من الكود ويؤثر مادياً في النتيجة أو السلامة. **الأصل هو طرح سؤال واحد فقط في كل مرة**؛ ويُسمح استثناءً بجمع حتى **3 أسئلة كحد أقصى في رسالة واحدة** فقط إذا كانت مستقلة تماماً وكان جمعها يوفر دورة محادثة كاملة.
- استخدم افتراضات معقولة ومعلنة بدلاً من إيقاف العمل بسبب تفاصيل صغيرة. إذا كانت المواصفات كافية، ابدأ مباشرة.
- **تدرج مسارات التخطيط**:
  - **L3 الكبير (Full SDD)**: تطبيق دورة Spec Kit الكاملة للميزات المعقدة والأنظمة الجديدة.
  - **L3 المتوسط (SDD-Lite)**: الاكتفاء بملف خطة موحد `docs/plans/<name>.md` يحدد الهدف والنطاق والمخاطر والتراجع، دون الحاجة لملفات العقود والبحوث الموسعة.
  - **L2 الحساس (Lightweight Chat Gate)**: أي تعديل على (ترحيلات SQL، سياسات RLS، الصلاحيات، الدفع، المصادقة) يتطلب عرض الفروقات/الاستعلام في الشات مع طلب موافقة كتابية صريحة قبل أي تطبيق.

- **مسار التخطيط والمواصفات (SDD Workflow)**:
  1. **المواصفات (`speckit-specify`)**: توليد مسودة المتطلبات وحالات الاستخدام في `spec.md`.
  2. **الاستيضاح (`speckit-clarify`)**: سد الفجوات عبر أسئلة مركزة مبنية على `spec.md` (أو `grill-me` كبديل استكشافي بسقف 3 أسئلة).
  3. **التصميم والخطة (`speckit-plan`)**: توليد خطة التنفيذ `plan.md` ونماذج البيانات والعقود.
  4. **بوابة الاعتماد الميكانيكية (Plannotator RTL Gate)**:
     - عند اكتمال صياغة الخطة/المواصفة، يُلزم الوكيل بتشغيل أداة المراجعة البصرية المعربة فوراً بناتج خارج مجلد المواصفة:
       `plannotator annotate <path-to-plan> --gate --json --result-file .mf/gate-result.json`
     - يُختم الملف ويُحسب تجزئة SHA-256 للملفات المعتمدة بالأمر الإلزامي:
       `node scripts/check-approval.mjs --seal specs/<name>/APPROVAL.json --from-result .mf/gate-result.json <ملفات...>`
     - يُلزم الوكيل بالتحقق من وجود `APPROVAL.json` ومطابقة بصمة SHA-256 للملفات المعتمدة عبر:
       `node scripts/check-approval.mjs`
     - **قاعدة منع الانحراف (Anti-Drift)**: أي تعديل يطرأ على الخطة أو اكتشاف حاجة لجدول جديد أو اعتمادية خارجية أثناء العمل، يُبطل الموافقة تلقائياً ويوقف التنفيذ حتى يُعتمد الفرق وتُعاد البوابة.
     - **المخاطر المتبقية وبوابة الاعتماد**: سكربت `scripts/check-approval.mjs` يكشف الانحراف ويمنع الحالات غير المعتمدة، لكنه لا يثبت وجود موافقة بشرية بمفرده. الضمان الحقيقي هو حماية الفرع على GitHub واشتراط الفحص الآلي (*Required status check* للفحص `Verify Spec Approval Integrity & Anti-Drift`). وللمطور الوحيد، لا يُفعّل *Require review from Code Owners* لتعذّر مراجعة الشخص لنفسه، ويُعتمد فحص الـ status check مع توثيق هذا الخطر المتبقي.
     - **عقد الاعتماد المقيّد بالنطاق والتوقيع الرقمي (`APPROVAL.json` Schema):**
       يجب أن يتضمن ملف `APPROVAL.json` الحقول الإلزامية التالية التي يتحقق منها `scripts/check-approval.mjs` والـ CI:
       - `approval_id`: معرّف فريد للموافقة (UUID).
       - `decision`: (`approved` أو `approved-with-notes` فقط).
       - `approver_id` & `approved_at`: هوية المطور المعتمد والطابع الزمني للإصدار.
       - `repository_id` & `environment`: معرّف المستودع والبيئة المستهدفة لمنع إعادة استخدام الموافقة في مشروع آخر.
       - `base_commit`: بصمة الـ Git Commit التي بُنيت عليها الخطة لمنع التنفيذ على شجرة كود متقادمة أو متعارضة.
       - `spec_hashes`: بصمات SHA-256 لكافة ملفات مجلد المواصفة `specs/<name>/`.
       - `allowed_paths`: مصفوفة مسارات محددة (Normalized Glob patterns) للملفات المسموح بتعديلها.
       - `expires_at`: وقت انتهاء صلاحية الموافقة.
       - `signature`: توقيع رقمي مشفر يثبت صدور الملف من المطور المخول.
     - **شروط التوقيع الرقمي لملف الاعتماد (Canonical JSON Signing):**
       لا يُخلط بين توقيع Git Commit وتوقيع ملف `APPROVAL.json`؛ يجب أن يخضع توقيع ملف الاعتماد للشروط الخمسة التالية:
       1. يوقع المحتوى بصيغة قياسية موحدة (**Canonical JSON**) لكافة حقول الاعتماد.
       2. يُستثنى حقل `signature` نفسه من الحمولة التي يُحسب عليها التوقيع.
       3. المفتاح الخاص بالتوقيع (Private Key) معزول تماماً ولا يملك الوكيل صلاحية الوصول إليه أو استدعائه.
       4. يتحقق الـ CI من صحة التوقيع مقابل قائمة المفاتيح العامة الموثوقة (Public Keys / Allowed Signers) المرتبطة بهويات المعتمدين (`approver_id`) وصلاحياتهم.
       5. يُرفض فوراً أي توقيع غير صالح، أو منتهي الصلاحية (`expires_at`)، أو صادر عن هوية غير مخولة.
     - **فحص النطاق الشامل (Strict Scope Validation):**
       يتحقق `check-approval.mjs` والـ CI من عدم تجاوز `allowed_paths` وفق تعريف تنفيذي صارم يشمل:
       1. الملفات المتتبعة (Tracked) والملفات الجديدة غير المتتبعة (Untracked).
       2. الملفات المتجاهلة بواسطة Git (`Ignored`) إذا كانت تقع ضمن مسارات الحراسة أو يمكن أن تؤثر في التنفيذ/البيئة.
       3. الروابط الرمزية (**Symlinks**)، مع إلزامية حل الرابط وفحص **المسار الحقيقي لوجهة الرابط (Resolved Target Path)** وليس اسم الرابط الظاهري فقط.
       4. تطبيع المسارات ورفض أي مسارات غير طبيعية أو محاولات خروج من جذر المستودع (`Path Traversal` عبر `../`).
       5. الملفات المعاد تسميتها (Renamed) أو المحذوفة (Deleted).
       6. التغييرات خارج المستودع عبر الأدوات أو السكربتات (تُضبط عبر `Change Surface Inventory`).
       7. **توقيت الفحص الإلزامي:** يُجرى الفحص النهائي في الـ CI على **النسخة الفعلية المراد دمجها (Actual Merge Commit / Tree)** وليس الاكتفاء بفحص شجرة العمل المحلية في مرحلة سابقة، لمنع اختلاف الحالة بين لحظة الفحص ولحظة الدمج (TOCTOU).
     - **حظر الختم الذاتي في بيئة بلا شاشة (Headless / SSH Anti-Spoofing):**
       يُحظر قطعيّاً على الوكيل إنشاء أو تعديل `.mf/gate-result.json` أو `APPROVAL.json` أو تمرير قرار الموافقة بنفسه. في بيئات SSH/Headless، يعرض الوكيل الخطة ويتوقف؛ ويقوم **المطور حصراً** بتشغيل أمر الاعتماد وتوقيعه خارج سياق الوكيل.
     - **مطابقة التنفيذ للمواصفات (Implementation Conformance):**
       سلامة بصمة `APPROVAL.json` تثبت عدم انحراف الخطة (`Spec Integrity`)، لكنها لا تثبت اكتمال المتطلبات. يجب ربط كل متطلب في `spec.md` بمعيار قبول واختبار فعلي في `tasks.md` يتم التحقق من نجاحه قبل إعلان الإنجاز.

- **جدول القرارات الحاسم (Decision Matrix)**:

| حالة الجلسة / القرار | السلوك الهندسي الإلزامي للوكيل |
|:---|:---|
| `"decision": "approved"` | تحقق من البصمة ثم تابع (الانتقال فوراً لتفكيك المهام عبر `speckit-tasks`). |
| `"decision": "approved-with-notes"` | اعرض الملاحظات عليّ. ما كان سؤالاً اسألني عنه، وما كان تعليمة أدرجه في `tasks.md` بعد تأكيدي. |
| `"decision": "feedback"` (طلب تعديل) | عدّل الخطة وأعد البوابة، بحد 3 دورات ثم التوقف. |
| إغلاق / خطأ / مهلة (Dismissed / Error / Timeout) | توقف، ولا كتابة كود نهائياً؛ كتابة تقرير بما جرى وانتظار توجيه المطور. |
| بيئة بلا متصفح (Headless / SSH / Subagent) | اكتشاف غياب الشاشة، توليد الخطة، عرضها داخل المحادثة كـ Artifact، وانتظار موافقة كتابية صريحة. |



- **تفكيك المهام والتنفيذ المنضبط**:
  - يتم تفكيك المهام عبر `speckit-tasks`، مع **اشتراط** أن تسبق مهام الاختبارات (TDD) مهام التنفيذ البرمجي في `tasks.md`.
  - التنفيذ يتم عبر `speckit-implement` باتباع دورة Red -> Green -> Refactor.

## 3. التوثيق الحي

قبل كتابة كود يعتمد على مكتبة أو API خارجي: افحص التوثيق الحالي للإصدار **المثبّت فعلاً** (أداة التوثيق في `skills-map.md`). تأكد من التواقيع، والتغييرات الكاسرة، والدوال المهملة. لا تعتمد على الذاكرة في إصدارات المكتبات.

تجاوز فقط إن لم تُستخدم مكتبات خارجية.

## 4. البناء والاختبارات (حسب المخاطرة)

- **منطق، أمان، صلاحيات، حسابات، تحويل بيانات**: اكتب الاختبار أولاً (Red → Green → Refactor). تأكد أنه **يفشل** قبل الإصلاح.
- **إصلاح خلل**: اختبار انحدار يفشل قبل الإصلاح وينجح بعده.
- **واجهة**: تحقق بصرياً/تفاعلياً (متصفح، لقطة شاشة، أو اختبار e2e للمسارات الحرجة). لا اختبارات وحدة صورية.
- **تعديل شكلي بحت (L0)**: لا اختبارات، يكفي البناء والعرض.
- اكتب أصغر شريحة تعمل، ثم كرّر. لا تبنِ ما لم يُطلب (YAGNI).

## 5. بوابات الجودة

طبّق الفحوصات المتناسبة مع المشروع ومخاطر التغيير. لا تفرض إعداداً مؤسسياً كاملاً على صفحة هبوط أو نموذج أولي صغير. لا تتجاوز فحصاً ضرورياً للسلامة أو لصحة السلوك لمجرد توفير التوكنز.

| البوابة | ما تفحصه | البديل إن لم تتوفر المهارة |
|:---|:---|:---|
| كود نظيف | تكرار، كود ميت، تعقيد زائد، تسمية، فصل المسؤوليات | مراجعة ذاتية بقائمة قصيرة + lint |
| اختبارات | هل تفشل فعلاً عند كسر السلوك؟ لا اختبارات بلا assertions أو تختبر الـ mocks فقط | مراجعة يدوية + (اختياري) كسر السلوك عمداً ورؤية الفشل |
| توثيق | مطابقة README/تعليقات/تعريفات API للسلوك الفعلي | مراجعة ذاتية |
| اختبار الواجهات | تحقق بصري وتفاعلي للمسارات الحرجة | تشغيل التطبيق محلياً وفحص المسار الرئيسي وحالات الخطأ والفراغ، أو اختبار e2e القائم، وإرفاق المخرجات |
| أمان | `security.md` — القسم المناسب لنوع التغيير | قائمة الفحص في `security.md` |

ملاحظة: SOLID/DRY ليست أهدافاً بذاتها. إن تعارضت مع البساطة (YAGNI) فالبساطة تغلب.

## 6. التحقق قبل إعلان الإنجاز

1. شغّل الأوامر الفعلية: build، test، lint، typecheck (ما ينطبق على المشروع).
2. أرفق المخرجات (أو مقتطفاً دالاً منها) في ردك.
3. للواجهات: شغّل التطبيق وتحقق من المسار الرئيسي وحالات الخطأ والفراغ.
4. اذكر صراحةً: ما تحققت منه، وما لم تتحقق منه، والفرضيات.
5. **تقييد حجم المخرجات (Log Truncation):** لحماية نافذة السياق من التضخم، لا تلصق سجلات البناء أو الاختبارات الكاملة؛ أرفق فقط الأسطر الدالة على النتيجة النهائية (مثل آخر 15–20 سطراً أو ملخص الفشل).
6. **بروتوكول إنعاش السياق (Context Refresh):** في مهام L3 الطويلة أو بعد حدوث ضغط تلقائي للمحادثة (Context Compaction)، يلتزم الوكيل بإعادة قراءة `SKILL.md` و `APPROVAL.json` و `tasks.md` قبل متابعة التعديل لضمان عدم نسيان القيود أو النطاق.

### عند الفشل

- أصلح السبب الجذري وأعد التشغيل. **حد أقصى 3 محاولات** لنفس الفشل، ثم توقف وقدّم تقريراً بما جرى وما جرّبته.
- **يُمنع** لتمرير الفحوصات: تعديل أو حذف اختبار قائم لإخفاء الفشل، تعطيل قواعد lint، إضافة `@ts-ignore`/`any` للتحايل، تخفيف الأمان. إن كان الاختبار خاطئاً حقاً فاشرح السبب واطلب موافقة المطور.

## 7. معايير عرضية

- **معالجة الأخطاء**: لا تبتلع الأخطاء بصمت؛ كل Promise له معالجة؛ رسائل خطأ للمستخدم لا تكشف تفاصيل داخلية.
- **الأنواع**: لا `any` بلا مبرر؛ تحقق وقت التشغيل عند حدود النظام.
- **الأداء**: اعتماديات قليلة، تجنب تضخم الحزم، لا استعلامات N+1.
- **الإتاحة**: راجع `ui-and-brand.md`.
- **السجلات**: بلا أسرار وبلا بيانات شخصية.
